## Bottom line

1. **The share link survives installation on Android, and almost certainly on iPhone, but iPhone has to be tested.**
   - **Android:** an installed app shares Chrome's storage. Links inside the app's scope also open in the installed app.
   - **iPhone:** the installed app is a sealed, separate copy. It starts at the manifest's `start_url`, and links never open it.
   - **iPhone start URL:** if the manifest leaves out `start_url`, WebKit's code uses the page's current URL, `#k=…` fragment included. Nobody has yet shown, on a real iOS 26/27 device, that the fragment is kept on the icon. **UNVERIFIED on a device.**
2. **New since the checkpoint doc: on iPhone, Safari copies the site's cookies into a new Home Screen app (iOS 17.2+), and nothing else** (WebKit Safari 17.2 post).
   - This is the only documented bridge from Safari to the installed app.
   - It could carry the "my lists" index, with a privacy cost explained in §3.4.
3. **No phone opens the keyboard without a tap, but the rules after that first tap differ, and that helps.**
   - **Android (Chromium code):** after any tap since the page loaded, a script's `focus()` raises the keyboard, even after an `await` or a timer.
   - **iPhone (WebKit code):** the focus has to happen during the tap, or move from one field to another while the keyboard is already up.
   - So: one tap minimum, then keep a field focused and the keyboard never drops.
4. **Voice:**
   - **Use the keyboard's own mic** on both phones.
   - **Android web voice button:** server-based, so online only. On-device mode is desktop only (BCD 8.1.6).
   - **iPhone Home Screen app:** a web voice button is effectively unusable. Apple said in 2021 that it is "not available" there. 2026 reports show it either silently returns nothing, or goes deaf after the first session.
   - **iPhone Safari tab:** WebKit asks for on-device recognition whenever the language supports it. So es-MX probably works offline in a Safari tab. **UNVERIFIED on a device.**
5. **Storage:**
   - Safari's 7-day wipe applies to Safari tabs. Installed iPhone apps keep their own day counter. **CONFIRMED.**
   - `navigator.storage.persist()` exists on both phones and is granted silently, with no prompt. Checkpoint1 never calls it.
   - The relay copy plus the link is the real backup.
6. **The offline cache (service worker) design is sound but has three cheap fixes:**
   - extend the background refresh with `event.waitUntil`;
   - bypass GitHub Pages' 10-minute HTTP cache on refresh;
   - pass through `pr-preview/`.
   - Safari 27 and Chrome Android 123+ also support service-worker **static routing**, which can serve the app shell before the service worker starts.
7. **Small features:**
   - **Wake lock:** works in installed iPhone apps since iOS 18.4, and on Android 84+.
   - **Vibration:** Android only, after a tap. iPhone has no vibration API; a direct tap on a real `<input type=checkbox switch>` still gives one haptic tick (iOS 26.5 closed the script path; REPORTED).
   - **Web Share:** works on both. Receiving shares from other apps (share target) works on Android only.
   - **Contact Picker:** Android only; behind a flag on iPhone. Not needed.
8. **The live site is not an installable app today.** On 2026-10-21:
   - `/listolista/sw.js` and `/listolista/manifest.webmanifest` return **404**;
   - `index.html` is 103,579 bytes, `Cache-Control: max-age=600`, `Last-Modified: Fri, 25 Sep 2026`.

## 3. `start_url`, `scope`, and how a shared-list link survives installation

### 3.1 What the spec and WebKit's code say
- **CONFIRMED (spec):** [W3C Web Application Manifest, Working Draft, 16 October 2026](https://www.w3.org/TR/2026/WD-appmanifest-20261016/):
  - start_url step 1 is "Set manifest["start_url"] to document URL". If `start_url` is missing or empty, that value stays.
  - **No step removes the fragment**, so `#k=…` is kept by spec.
  - The default scope is "the start URL, but with its filename, query, and fragment removed".
  - `id` defaults to `start_url`; a declared `id` has its fragment removed.
  - `start_url` is "purely advisory", and the user agent MAY let the user edit it.
- **CODE (WebKit main, last commit 2026-09-04):** `Source/WebCore/Modules/applicationmanifest/ApplicationManifestParser.cpp`
  - `parseStartURL`: a missing, empty, invalid or cross-origin `start_url` returns `documentURL` (lines 153-181).
  - A missing scope falls back to `URL { startURL, "./" }` (lines 112-116).
  - A missing `id` returns `startURL` **with its fragment** (lines 464-477). Only an explicit `id` gets `removeFragmentIdentifier()` (line 491).
  - So with checkpoint1's iOS manifest, each list's icon would get its own `id`, including the secret.
- **CODE:** the `documentURL` that WebKit passes in is `DocumentLoader::url()` (`Source/WebCore/loader/ApplicationManifestLoader.cpp:122`).
  - `history.replaceState` and hash navigations update it (`Document::updateURLForPushOrReplaceState` → `replaceRequestURLForSameDocumentNavigation`, `Document.cpp:8974-8985`; `DocumentLoader.cpp:254-258`; `FrameLoader.cpp:1378`, `:1406`).
  - **But the processed manifest is cached once per page load** (`ApplicationManifestLoader::processManifest`, lines 117-128: `if (!m_processedManifest)`).
  - When Safari's closed-source shell first asks for the manifest is **UNVERIFIED**.
  - **Risk (inference):** if Safari reads the manifest at page load, the saved start URL is the URL the page *loaded* with:
    - a list opened from a WhatsApp link already has `#k=` at load, so it is fine;
    - a list that became shared later in the same session (`share()` → `replaceState('#k=…')`, `src/app.js:527-531` and `:159`) may be saved without its key.
  - Cheap mitigation: before showing the iPhone install hint, if the hash changed since load, call `location.reload()`. A reload creates a new loader and a fresh manifest.

### 3.2 What happens on iPhone
- **CONFIRMED:** a Home Screen app does not share storage with Safari: "The current behavior (on Apple platforms) is by design. Home Screen apps are created as isolated entities" ([WebKit bug 181849, comment 3, 2022-02-01](https://bugs.webkit.org/show_bug.cgi?id=181849); still NEW, last modified 2022-06-14).
  - firt.dev (13 Oct 2026): "Storage shared with Browser ❌".
  - web.dev: "Each installation has its own isolated storage and is treated as a different application" ([Learn PWA: Installation, 2024-09-20](https://web.dev/learn/pwa/installation/)).
- **CONFIRMED (new):** "when they tap 'Add to Home Screen' and create a web app, the cookies are copied over… No other kind of local storage is copied over", and afterwards "no other website data is shared" ([WebKit Features in Safari 17.2](https://webkit.org/blog/14787/webkit-features-in-safari-17-2/)). firt.dev: "Login cookies copied to the installed app ✅ 17.2".
- **CONFIRMED:** iOS honours `start_url` when it is set:
  - BCD: `safari_ios` 11.3.
  - [GitLab issue 427560](https://gitlab.com/gitlab-org/gitlab/-/issues/427560): the add sheet shows the manifest URL.
  - [hypr-remote issue #1, 2026-09-28](https://github.com/uzayr-iqbal-hamid/hypr-remote/issues/1): "`start_url": "/"`, so the `?t=` parameter is dropped".
- **REPORTED, not device-tested:** two 2026 projects describe the same fix, putting the credential in `start_url`. Neither tested it on a real iPhone:
  - the hypr-remote issue says that without `start_url` "iOS then falls back to the URL that was in the address bar at install time";
  - [agy-remote commit f2b395e (2026-08-22)](https://github.com/ollisulopuisto/agy-remote/commit/f2b395efc3b1f07c51d2b90514ed07f54f3baf35) serves a dynamic manifest with `start_url` `/?token=…#key=…`, and says only "Verified in a browser".
- **CONFIRMED:** iPhone has **no link capturing**. firt.dev: "Link Capturing ❌ Only a push message can open an installed PWA", and out-of-scope links open in an in-app browser.
  - Consequence for ListoLista: when someone who already has the icon receives a *new* list link in WhatsApp, it opens in Safari (or an in-app view), never in their installed app.
  - The installed app therefore needs a "Pegar enlace de la lista" path: a plain text field plus the system paste works without any API. Alternatively the person adds a second icon, but each icon has its own storage.
- **Checkpoint1 gotcha (code reading):** an icon added while a *local* list (`#l=<id>`) is open opens an empty new list inside the app. `start()` opens `#l` only if that list is in storage (`src/app.js:642`), and the app's storage starts empty. Only `#k=` lists can be restored, because their content comes back from the relay.

## 4. Storage persistence and eviction

- **CONFIRMED:** Safari deletes "all of a website's script-writable storage after seven days of Safari use without user interaction on the site". "Web applications added to the home screen are not part of Safari and thus have their own counter of days of use." Source: [WebKit, Full Third-Party Cookie Blocking and More, 2020-03-24](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/) [older].
  - MDN (modified 2026-01-05) adds that it applies "when cross-site tracking prevention is turned on", and that "Cookies set by server are exempt" ([Storage quotas and eviction criteria](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)).
- **CONFIRMED:** `navigator.storage.persist()` and `persisted()` are in iOS Safari 15.2+ and Chrome Android 55+; `estimate()` in iOS 17+ and Android 61+ (BCD 8.1.6).
  - "Safari and most Chromium-based browsers… automatically approve or deny the request based on the user's history of interaction with the site and do not show any prompts" (MDN).
  - WebKit "grants a request based on heuristics like whether the website is opened as a Home Screen Web App" ([WebKit, Updates to Storage Policy, 2023-08-10](https://webkit.org/blog/14403/updates-to-storage-policy/)).
- **CONFIRMED:** origins granted persistence are skipped by **storage-pressure** eviction (MDN; WebKit 2023). Whether `persist()` also protects a Safari tab from the **7-day** deletion is still **not stated** by any source (unchanged from the checkpoint doc).
- **CONFIRMED:** quotas in Safari 17+: an origin may use up to about 60% of disk, and Home Screen apps get the same as the browser (MDN; WebKit 2023).
- **From the checkpoint doc, not re-checked:** `vdm285.github.io` hosts four of Victor's projects. They share one origin, so they share one storage area and quota, and "clear site data" clears all of them. Keep `listolista_`-prefixed keys.
- **Implication:** checkpoint1 never calls `persist()`.
  - The rebuild should call it once in the installed app (`display-mode: standalone`, supported in iOS 12.2+ and Chrome Android 42+ per BCD).
  - It should treat the relay copy plus the link as the backup, and offer export.

## 5. Service worker caching strategy

What checkpoint1 got right:
- one service worker at `/listolista/sw.js`, whose default scope is its own folder;
- shell served from cache first, so offline start works;
- versioned cache with old caches deleted;
- registration only on `https:`.

GitHub Pages cannot send `Service-Worker-Allowed` (checkpoint doc; [MDN register(), modified 2026-10-12](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerContainer/register) confirms the scope rule).

Findings for the rebuild:
1. **The background refresh is not kept alive** (`src/sw.js:21-27`).
   - The `net` promise is not passed to `e.waitUntil()`. When the cached copy answers, the service worker may be stopped before `cache.put` finishes: "The lifetime of a service worker is tied to the execution lifetime of events" ([Service Workers, Editor's Draft, 2026-09-17](https://w3c.github.io/ServiceWorker/) §2.1.1).
   - The well-known [offline cookbook](https://web.dev/articles/offline-cookbook) sample (2014) has the same omission.
   - Fix: `e.waitUntil(net.catch(()=>{}))`.
2. **The refresh goes through GitHub Pages' HTTP cache.** Live headers on 2026-10-21: `Cache-Control: max-age=600`, an `ETag`, HSTS.
   - `fetch(req)` inside the service worker can be answered by a 10-minute-old HTTP-cache copy, which delays a new version by one more open.
   - Fix: `fetch(req, {cache: 'no-cache'})`. The server's ETag makes this a cheap revalidation.
   - The service worker *script* itself is fine: `updateViaCache` defaults to `"imports"`, so the main script is always fetched from the network on update checks. A registration counts as stale after 86400 s (SW spec).
3. **`pr-preview/` is not passed through.** The check at `src/sw.js:19-20` only excludes other origins and out-of-scope paths, and `/listolista/pr-preview/pr-N/` is inside the scope. The checkpoint doc's recommendation 4 asked for this. Add `if (url.pathname.includes('/pr-preview/')) return;`.
4. **Offline navigation to an uncached path** returns `undefined` to `respondWith`, which becomes a network error (`src/sw.js:24-25`). Fall back to the cached `./` for `mode === 'navigate'`.
5. **`ignoreSearch: true` is right.**
   - Old `?room=` links map to `./`.
   - Fragments are never sent to the network, so `#k=` secrets never reach GitHub or a cache key. (General URL and HTTP behaviour, not re-sourced.)
6. **New option, static routing.** `InstallEvent.addRoutes` is in **Safari 27** and **Chrome Android 123** (BCD 8.1.6; WebKit 27 post).
   - It can tell the browser to serve the shell from cache without starting the service worker first. The checkpoint doc cites about 250 ms service-worker start-up on mobile ([web.dev 2017](https://web.dev/blog/navigation-preload), older).
   - Use it as a progressive enhancement after feature detection. Support for its sub-options: **UNVERIFIED**.
7. **Cache version:** only `index.html` is hashed (`build.py:33-36`). That is acceptable with stale-while-revalidate; to be tidy, hash every shell file.
8. **`skipWaiting` + `clients.claim`** (`src/sw.js:9`, `:15`): together with stale-while-revalidate, a new version appears on the *next* open, as the comment says (`src/sw.js:2`). iPhone often kills background apps, so "next open" comes soon. Showing a "Nueva versión lista" note is optional.

## 6. Keyboard focus on load: can a page raise the keyboard without a tap?

**No, on both phones. The details below change the design.**

### iPhone
- **CONFIRMED (BCD 8.1.6):** `focus()` without user interaction "has no effect" when no hardware keyboard is attached; `autofocus` (iOS 16.4+) "has no effect" without a hardware keyboard.
- **CONFIRMED:** [WebKit bug 195884](https://bugs.webkit.org/show_bug.cgi?id=195884), "Autofocus on text input does not show keyboard", is NEW (last modified 2024-03-19). An Apple engineer wrote on 2019-03-19: "We (Apple) like the current behavior and do not want programmatic focus to bring up the keyboard".
- **CODE (WebKit main, `Source/WebKit/UIProcess/ios/WKContentViewInteraction.mm`, last commit 2026-10-19, lines 8554-8590):** by default the keyboard is shown only if:
  - `userIsInteracting` (the focus happens while handling a tap); or
  - the web view is already first responder and focus is **changing from an already focused element** (`_isChangingFocus`), or a hardware keyboard is in use.
  - A private delegate policy can force Allow or Disallow; what Safari's shell sets is **UNVERIFIED**.
  - **Design consequence:** keep the *same* input focused after Enter (checkpoint1 does, `src/app.js:230`). Moving focus to another field while the keyboard is up keeps it up. Call `focus()` synchronously inside the tap handler.
- **CONFIRMED:** [WebKit bug 279904](https://bugs.webkit.org/show_bug.cgi?id=279904): the keyboard did not appear in installed apps after upgrading to iOS 18. It is NEW, last modified 2024-12-11, never reproduced by WebKit, with no iOS 26/27 reports. Include it in the device test.

### Android (Chrome)
- **CODE (Chromium main, `third_party/blink/renderer/core/dom/element.cc`, last commit 2026-10-19, lines 8778-8785):** after focus succeeds, `ShowVirtualKeyboardOnElementFocus` is called only `if (GetDocument().GetFrame()->HasStickyUserActivation())`. The comment says: "for now we match IE's heuristic and bring up the keyboard if there's been any gesture since load".
  - **Cold start:** no keyboard.
  - **After the first tap anywhere:** a later script `focus()`, even after `await` or a timer, raises the keyboard.
  - This answers the checkpoint doc's open question 13 at code level.
- **CONFIRMED:** `navigator.virtualKeyboard.show()` is in Chrome Android 94+ and not in Safari (BCD). Per the spec it aborts if the window "does not have sticky activation", and it needs `virtualkeyboardpolicy="manual"` ([VirtualKeyboard API, W3C Working Draft, 2022-05-05](https://www.w3.org/TR/virtual-keyboard/), older). It adds nothing for a cold start.
- **UNVERIFIED:** whether launching the installed app from its icon counts as a user gesture inside the page. The code suggests not, because a new page load starts without sticky activation.
- **Small items:**
  - `interactive-widget` in the viewport meta (Chrome Android 108+, not iOS; BCD) controls whether the keyboard resizes the page.
  - `enterkeyhint="done"` (`src/app.html:143-144`) may make some Android keyboards close on Enter. "enter" or "next" fits a Notepad-style list better. **UNVERIFIED.**

## 9. Web Share and clipboard

## 12. iPhone gotchas (checklist)

1. **Separate world:** the Home Screen app shares nothing with Safari except cookies copied once at install (17.2+), and each icon has its own storage.
2. **Links never open the installed app** (no link capturing). Plan an in-app "Pegar enlace".
3. **The icon opens `start_url`.**
   - Without it, the fragment probably survives (spec and WebKit code), but there is no device proof.
   - WebKit computes the start URL once per page load: reload after changing the hash, before the user installs.
4. **No install button;** a hint only. A user can turn off "Open as Web App" and get a Safari bookmark instead.
5. **Keyboard:** one tap; focus synchronously in the handler; keep it focused. Bug 279904 is a possible installed-app keyboard failure.
6. **Speech:** do not rely on it in the installed app or in Safari View Controller.
7. **Wake lock** in the app needs iOS 18.4+.
8. **Haptics:** no vibrate; switch-tap tick only, single tick since 26.5 (REPORTED).
9. **Manifest:** iOS ignores `lang` (firt.dev); `apple-touch-icon` overrides manifest icons; no `shortcuts` or `share_target`.
10. **7-day wipe** for Safari-tab-only users. A user who only ever opens the WhatsApp link in Safari can lose local-only lists.
11. **Badging and notifications** only in Home Screen apps, and notifications only through a service worker (BCD). Push is the only thing that can open the installed app (firt.dev), and it needs a sender server, which is outside this scope.
12. **Status bar `black-translucent`:** one developer reported a Liquid Glass blur on iOS 27 (single report from the checkpoint doc, not re-checked). Keep `default`.
13. **`visibilitychange`:** fully supported on iOS only since 14.5; it does not fire when navigating away, so also handle `pagehide` (BCD note). `freeze` is not on iOS. Checkpoint1 already handles `pagehide`.

## 13. Android gotchas

1. **"Instalar" needs criteria plus engagement:** a tap and about 30 s before `beforeinstallprompt`. The manifest must keep `start_url`.
2. **Installed app equals Chrome's storage, and in-scope links open the app.** WhatsApp's routing is unverified.
3. **Speech is online only, and `continuous` is ignored.**
4. **Vibration only after a gesture.**
5. **The keyboard follows sticky activation** (the first tap unlocks later programmatic focus).
6. **Android WebView** (in-app browsers) lacks Web Share (BCD).
