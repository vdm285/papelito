# ListoLista sync: what exists, what we learned, and a design with no server (2026-10-21)

- **Scope:** how the live site syncs today (`old/main`), what the September rebuild built (`old/checkpoint1`), how much of it needs a server, and the best design for a sync layer with **no server the owner runs**.
- **Method:** I read every file named in the task in full. I ran the old tests under Node. I wrote small demos of the old merge bugs, ran read-only probes of public Nostr relays and MQTT brokers, and built and stress-tested a prototype of the proposed merge.
- **Labels:** "verified" means I checked it myself today. "Sibling probe" means a parallel agent ran it today; its files are in `data/cache/probes/`, and I read the results but did not re-run them. "Unverified" means nobody checked it.
- All paths are relative to `D:\_GitHub\listolista\data\cache\`.

## 0. Bottom line

1. **Today's live site** syncs each shared list as **one plaintext, retained MQTT message** on the public HiveMQ broker, on topic `listolista/v2/<room>/data`.
   - The merge rule is per-item "newest wall-clock timestamp wins", and deletions are soft flags that are never removed.
   - A phone whose clock runs slow cannot strike an item last stamped by a phone whose clock runs fast: its tap is undone on the next sync (demo, §2.4).
   - Measured today: HiveMQ holds **0** retained ListoLista messages, so the old plaintext copies are gone. Why they are gone is unverified.
2. **Checkpoint 1** kept the same per-item rule but improved it:
   - Edits use `max(now, old+1)` timestamps.
   - Deleted items stay as markers ("tombstones") for 60 days, then are removed.
   - The relay sees only encrypted blobs: AES-GCM-256 with a key derived by HKDF from a 128-bit secret in `#k=`, padded to 1 KB steps, plus a write token.
   - **The merge still has four real bugs,** shown by running code (§3.6):
     - Equal timestamps leave the two phones permanently different.
     - A strike and a text edit made at the same time: one is lost.
     - A phone offline for more than 60 days brings deleted items back.
     - Timestamps are clamped against each receiving phone's own clock, so phones can disagree.
3. **Checkpoint 1's sync depends entirely on Victor's Cloudflare Worker + Durable Object** (`relay/`).
   - Its protocol needs a server that does compare-and-set on a version number and checks the write token. No public relay offers either.
   - Without the Worker, the app just shows "offline" (`src/app.js:169`).
   - So the transport and the merge must be redesigned, not just pointed at a new address.
4. **Recommended design (zero servers, zero cost, private, converges):**
   - **(a) One slot per phone.** Each phone publishes its *whole merged copy* of the list as its own replaceable record. Each phone owns its slot, so no compare-and-set is needed and no update is lost.
   - **(b) A merge with clean math.** The copy is a state-based CRDT: last-writer-wins per field, ordered by hybrid clock stamps with the device id as tie-break, and deletes that need **no tombstones**, using a per-device "seen" map (an optimized OR-set).
   - **(c) Carried by Nostr NIP-78 kind 30078** on 4-5 public relays from different operators. The signing key is derived from the link secret, so only link holders can write.
   - **(d) Optional fallback:** an encrypted, retained, per-device topic on a public MQTT broker.
   - The prototype passed scenario tests for all four old bugs, 3,000 + 1,000 randomized runs (3 devices, skewed clocks, a relay that loses and replays copies) with no divergence and no deleted item coming back, and checks of the merge laws. Two deliberately broken controls were caught (§7).
5. **Public Nostr relays work today for this, with caveats** (§4):
   - Of 24 relays probed, 17 opened a WebSocket, and none of those asked for login (AUTH). Most serve kind 30078 openly. Several hold such events older than 1 year, and 5 hold them older than 3 years.
   - The sibling probe found 14 relays that accepted kind-30078 writes from a brand-new key without login, plus 2 more that accepted only the first writes; most of them read the event back and replaced it correctly.
   - Some relays refuse new keys (web-of-trust, paid, NIP-05, or "kind not allowed").
   - Relays promise no retention, so **the phones are the store and the relays are the mailbox.**

## 2. How the live site syncs today (`old/main/index.html`)

### 2.1 Transport and topic scheme

- **Broker:** `wss://broker.hivemq.com:8884/mqtt` (`index.html:260`).
- **Library:** mqtt.js `mqtt@5.16.0` from unpkg, pinned with an SRI hash. It is loaded lazily, only for shared lists (`index.html:263-266, 313-326, 328-336`). This is the 2026-09-25 safety patch.
- **Topic:** `listolista/v2/${room}/data` (`index.html:365-367`). The room comes from the **query string** `?room=` (`index.html:358-364`), so it reaches GitHub's servers and browser history.
  - New rooms are `'room_' + randomId()`, 16 random bytes in hex (`index.html:300-304, 412`).
  - Older links used a timestamp id; anyone can join any id typed by hand (`index.html:484-487`).
- **Connection:** reconnects every 2 s, connect timeout 10 s (`index.html:561`).
- **Sandbox** (`main/sandbox.html:197-200`): earlier topics `listolista/v6/<room>/data|drafts|alive` with presence heartbeats; the room is `'room_' + Date.now().toString(36)` (`sandbox.html:184`).

### 2.2 Payload

- The **whole app state as plaintext JSON**, published **retained** at QoS 0 (`index.html:637`).
- State shape (`index.html:272-275`):
  - `items[]`: `{id, text, category, done, deleted, timestamp, lastAuthor}`
  - `meta`: `{title, timestamp, lastAuthor}`
- `id` is `Date.now()` and `timestamp` is `Date.now()` (`index.html:519-525`). `lastAuthor` is `'User_' + random(1000)` (`index.html:277`).
- The title publishes the whole state on **every keystroke** (`index.html:391-398`).

### 2.3 Merge rule (`handleSync`, `index.html:585-627`)

- **Items:**
  - The union by `id`.
  - For an id on both sides, the remote copy wins only if `rItem.timestamp > lItem.timestamp`, strictly (`index.html:609-615`). A tie keeps the local copy.
- **Deletion:** a soft flag, `deleted: true` plus a new timestamp (`index.html:550-552`). "Clear done" and "wipe" do the same (`index.html:448-482`). These tombstones are **never purged**.
- **Meta:** the whole object, by `meta.timestamp` (`index.html:597-606`).
- **When it publishes** (`index.html:563-575, 629-638`):
  - It waits for the retained snapshot, or 2.5 s with none.
  - After merging, it re-publishes only if it holds something newer (`localNewer`, `index.html:590-595, 626`).
  - Remote input is barely checked: `handleSync` only tests `Array.isArray(items)` (`index.html:586`). Rendering uses `textContent` (`index.html:747, 753, 675`), so the old title-injection hole (research P3) is closed.

### 2.4 Problems in today's live sync (verified by reading and by demo)

| # | Problem | Evidence |
|---|---|---|
| L1 | Plaintext on a public broker. Anyone who knows the prefix can read, overwrite or wipe a list | `index.html:637`. HiveMQ granted `listolista/#` to my probe today (§4.2) |
| L2 | A phone with a slow clock cannot change an item last stamped by a fast clock: its tap is undone on the next snapshot | `index.html:539` sets `Date.now()`; `index.html:611` lets the larger remote win. Demo 4 in `work/sync/old-tests.mjs`: output "remote (tap undone)" |
| L3 | A tie keeps the local copy on each phone, so the phones never agree | `index.html:611`, strict `>` |
| L4 | Tombstones grow forever, and so does the retained message | `index.html:550`, no purge |
| L5 | One shared retained slot. If both phones publish and then go offline before seeing each other's message, an update is lost from the broker (local copies keep it) | `index.html:637`, analysis §6.1 |
| L6 | The room id travels in `?room=` (server logs, history) | `index.html:358-359, 416` |

**Measured today** (`work/sync/probe-mqtt.mjs`, 2026-10-22T04:39Z, subscribe-only):
- HiveMQ **granted** `listolista/#` and returned **0 retained messages**. The 9 plaintext snapshots counted on 2026-09-25 are gone.
- Whether `tools/erase-broker-lists.sh --erase` was run, or HiveMQ dropped them, is **unverified**.
- Any phone that opens an old shared list will publish its plaintext copy again (`index.html:573, 626`).

### 3.2 Crypto design (`src/sync.js`)

- **Secret:** 16 random bytes, base64url (22 characters), carried in `#k=<secret>` (`sync.js:30`; `app.js:159, 535`).
- **Room id:** `base64url(SHA-256("listolista/room/v1" ‖ secret)).slice(0,22)`, about 132 bits (`sync.js:35-36`).
- **Encryption key:** HKDF-SHA-256 with salt `"listolista"` and info `"aes-gcm-256/v1"`, giving an AES-GCM-256 key that cannot be exported (`sync.js:37-40`).
- **Write token:** HKDF with info `"write-token/v1"`, 128 bits (`sync.js:41`).
  - The relay stores `SHA-256(tok)` on the **first** write (trust on first use) and rejects later writes with a different token (`relay/src/index.js:12-13, 85-86`).
  - The token is sent in every `put` (`sync.js:145`).
- **Sealing:**
  - A fresh 12-byte IV for every message. The additional authenticated data is the room id, so a blob cannot be moved to another room.
  - The plaintext is a 4-byte big-endian length, then the JSON, padded with zeros to a multiple of **1,024 bytes** (`sync.js:14, 45-62`).
  - Wire format: `"v1.<iv>.<ct>"`. `open()` rejects any other version, tampering, the wrong key and the wrong room (`sync.js:64-70`; tests `sync.test.mjs:23-34`).
- **Measured** (`work/sync/old-tests.mjs`): 0 or 10 items → 1,407 characters; 40 items → 5,503; 100 → 12,330; 300 → 35,540. So 1 KB steps hide small changes but still reveal the rough size class.
- **Gaps (verified by reading):**
  - The authenticated data binds no version or sequence number, so an old blob can be replayed. The research admits this (line 255). On the old Worker it is limited by compare-and-set (`index.js:87`).
  - A "decrypt" error is reported (`sync.js:102-104`) but the app ignores it (`app.js:174-177`). The relay version is still updated (`sync.js:98`), so this phone's next `put` overwrites a blob it could not read, for example one from a newer app version.

### 3.3 Relay protocol (`relay/src/index.js`, `relay/wrangler.jsonc`)

- **Messages:** one WebSocket per phone at `/r/<roomId>`. The server sends `{t:'snap', v, blob}` on connect and after every accepted write, to every phone. The phone sends `{t:'put', base, blob, tok}`. The server answers `conflict` (with the current blob) when `base !== v`, or `err` with `too_big`, `forbidden`, `slow_down` or `bad_request` (`index.js:5-14, 52-94`).
- **Limits:** blobs up to 64 KB; at most 30 puts per phone per 10 s; heartbeat `"ping"` → `"pong"` answered without waking the object (`setWebSocketAutoResponse`, `index.js:18-20, 49`).
- **Expiry:** an alarm deletes any list untouched for 180 days (`index.js:21, 91, 100-102`).
- **Origin check:** only the origins in `ALLOWED_ORIGINS` may connect (`wrangler.jsonc:8`); clients that send no Origin are let through (`index.js:23-26`).
- **Storage:** one SQLite-backed Durable Object class `Room` (`wrangler.jsonc:6-7`).
- **Possible race (unverified):**
  - `webSocketMessage` reads the stored version, awaits `crypto.subtle.digest`, then writes (`index.js:84-90`).
  - If the Durable Object lets another message run during the digest await, two puts with the same `base` could both be accepted. Whether workerd keeps the object closed to other events across a non-storage await is **unverified**.
  - Phones would heal this through `localNewer` re-puts while online.
- **Phone side** (`sync.js:76-169`):
  - Backoff of 1-8 s; app ping every 20 s with an 8 s pong timeout; a 6 s timeout for an answer to a put; a fresh connection on wake (`app.js:613-618`).
  - A remote copy arriving while a put is in flight causes extra puts (`sync.js:96-105` with `139-150`). That is wasted traffic, not a correctness bug.

### 3.4 Merge semantics (`src/merge.js` + `src/app.js`)

- **Items** (`merge.js:47-90`):
  - The union by id. For an id on both sides, the **whole item** with the larger `timestamp` wins; **a tie keeps the local copy**.
  - Order: local order first, then items found only in the remote copy.
- **Meta:** last-writer-wins on the whole object (`merge.js:92-112`). **Aisle corrections (`ovr`):** last-writer-wins per key (`merge.js:114-151`). **Aisle order:** last-writer-wins on the whole object (`merge.js:153-176`).
- **Clock:** `bump(old) = max(Date.now(), old + 1)` per item (`app.js:28-29`, used at `239, 244, 250, 256, 265`). New items get `t + k` (`app.js:223-225`). **No device id breaks ties.**
- **Tombstones:** `deleted: true` markers. On the wire they shrink to `{id, deleted, timestamp}` (`app.js:69-76`), and they are **purged after 60 days** (`app.js:30, 63-67`). The code comment admits that a phone offline for longer can bring an item back (line 63).
- **Clamp:** `sanitize()` clamps every incoming timestamp to the receiving phone's `now + 24 h` (`app.js:36-37`). The result depends on the receiver's clock.
- **Merge points:**
  - Before each save, the stored copy is merged in (`app.js:117-121`).
  - On each relay copy (`app.js:181-196`, re-putting when `localNewer`).
  - On storage events from other tabs (`app.js:620-628`).

### 3.7 How much depends on a server the owner runs

**All of it.**
- The relay address is baked in at build time (`src/app.html:162`; the built `index.html:801` holds `wss://listolista-relay.vdm285.workers.dev`). An empty relay address means "offline" (`app.js:169`). There is no second transport.
- The protocol's safety relies on two things only a server provides:
  1. compare-and-set on `v` (`index.js:87`);
  2. checking the write token on the server (`index.js:85-86`).
- Running it needs:
  - a Cloudflare account (created, `ROADMAP.md:50`);
  - `wrangler login` and deploys (`tools/deploy.sh`);
  - a Durable Object migration (`wrangler.jsonc:7`), an origin allow-list (`wrangler.jsonc:8`), and the free-plan quotas (research lines 96-122).
- The phone-side encryption (`seal`/`open`/`derive`) and `merge.js` do not depend on the server and can be reused in spirit. The `Relay` class cannot.

### 4.2 Public MQTT brokers

**My probe** (subscribe-only, using my own ~60-line MQTT 3.1.1-over-WebSocket client, `work/sync/probe-mqtt.mjs`):

## 6. Recommended design

### 6.1 Shape: "every phone carries the whole list, and each writes on its own sheet"

- **The list lives on the phones.** Every phone stores the full list state and draws from it synchronously at start-up, so the Notepad benchmark holds.
- **Each phone publishes its full merged state to its own slot.** On Nostr this is an addressable event keyed by (kind 30078, list pubkey, d = that device's slot tag). Relays keep only the newest per slot (NIP-01, `work/sync/specs/nip01.md:99-101`).
- **Every phone subscribes to all slots of the list** (`authors: [listPubkey]`) and merges every record it receives.
- **Why per-device slots:** public relays have no compare-and-set. With one shared slot, the last writer wins at the relay. If that writer had not yet seen the other phone's edit, and the other phone is then in a pocket, that edit is missing from the relay (prototype check "one shared slot loses A's item"). With per-device slots no slot is ever written by two phones, so nothing is lost, and **any one surviving slot holds the whole list**.
- **Why a state-based CRDT:** relays may lose, duplicate, reorder or replay records. A merge that is commutative, associative and idempotent makes all of that harmless. Every phone that has seen the same set of records shows the same list, in any order, with any duplicates.

### 6.2 Keys derived from the link secret

- **Link:** keep `https://<site>/#k=<22 characters>`, a 128-bit random secret.
- **Derivation:** HKDF-SHA-256 with salt `"listolista/v2"` and different `info` strings, so nothing collides with v1:

| info | Output | Use |
|---|---|---|
| `"enc"` | AES-GCM-256 key, not exportable | Encrypts every record |
| `"sign"` | 32 bytes → secp256k1 secret key; re-derive with `"sign/1"` in the 2⁻¹²⁸ case that it is out of range | Signs Nostr events. `listPubkey = schnorr.getPublicKey(sk)` |
| `"slot"` | HMAC key | `slotTag = hex(HMAC(slotKey, deviceId))[0:32]`, so relays never see device ids |
| `"mqtt"` | 22-character topic root | Only if the MQTT fallback is used |

- Only link holders can write a slot. No outsider can replace, delete (NIP-09 needs the same pubkey) or forge one.
- The same key answers NIP-42 AUTH, which satisfies the new NIP-78 "owner only" rule.
- A future "view only" link could carry the encryption key and the pubkey but not the signing key. That is not needed now.

### 6.3 Data model: the plaintext inside each record

```json
{
  "v": 2,
  "clk": "0mh2k9x1a.k3f9a2c1",
  "seen": { "k3f9a2c1": "0mh2k9x0z.k3f9a2c1", "p7x2m0qd": "0mh2k7b3c.p7x2m0qd" },
  "title": ["SÚPER", "0mh2k1000.p7x2m0qd"],
  "items": {
    "0mh2k7b3c.p7x2m0qd": { "t": ["huevos", "0mh2k7b3c.p7x2m0qd"], "d": [1, "0mh2k9x1a.k3f9a2c1"] },
    "0mh2k9x0z.k3f9a2c1": { "t": ["leche", "0mh2k9x0z.k3f9a2c1"], "d": [0, "0mh2k9x0z.k3f9a2c1"],
                            "p": ["0mh2k9x0z", "0mh2k9x0z.k3f9a2c1"] }
  },
  "ovr":   { "pan molido": ["DES", "0mh2k8aaa.k3f9a2c1"] },
  "order": [["FRU", "PAN", "LAC"], "0mh2k0zzz.p7x2m0qd"]
}
```

- **Stamp** = `<milliseconds in base36, 9 characters>.<deviceId>`, compared as plain strings: time first, then device id as a deterministic tie-break.
  - A device stamps an edit with `max(wall-clock ms, clk + 1)` and raises `clk` to the largest stamp it has merged, including the `seen` values.
  - This is a simplified hybrid logical clock (Kulkarni et al., "Logical Physical Clocks…", https://cse.buffalo.edu/tech-reports/2014-04.pdf). It never goes behind anything already seen, so a slow phone's tap always wins over the value it saw (fixes L2, B1, B4). Offline edits keep "latest real time wins" order.
  - Stamps are never shown to users as times.
- **deviceId:** 8 random base36 characters, created once per installation and stored next to the list. A phone that lost its storage simply becomes a new device.
- **Item id** = the item's birth stamp, so the id also tells which device created it and when.
- **Registers:** every field is a `[value, stamp]` register, last writer wins per field (fixes B2).
  - `t` text, `d` done.
  - Optional: `p` sort position (for undo and "paper" order), and any future per-item field such as a quantity or aisle.
  - List level: `title`, per-key `ovr`, whole `order`.
- **Deleting an item** removes it from `items`. **No tombstone is kept.**
  - `seen[dev]` records the newest birth stamp from each device that this copy has absorbed.
  - During a merge, an item one side lacks is taken from the other side **only if the lacking side has not seen its birth**. Otherwise the lacking side deleted it.
  - This is the optimized OR-set of Bieniusa et al. (https://arxiv.org/abs/1210.3368); see also delta-state CRDTs (https://arxiv.org/abs/1603.01529).
  - The list's size depends only on its live items plus about 30 bytes per device ever used. No purge window, no tombstones coming back (fixes B3, L4).
- **Semantics this gives:**
  - Concurrent adds both survive.
  - A text edit and a strike made at the same time both survive.
  - Delete vs. a concurrent edit: **delete wins**.
  - "Vaciar lista" on one phone does not remove items another phone added offline that the first phone never saw.
  - **Undo** creates a new item with a new id, copying `t`, `d` and `p`. Re-using the old id would be undone again by the other phones.

### 6.4 Merge rule (tested prototype: `work/sync/proposed-merge.mjs`, about 60 lines)

```
merge(a, b):
  seen  = per-device max(a.seen, b.seen)
  clk   = max(a.clk, b.clk, all seen values)
  title = lww(a.title, b.title);  order = lww(...);  ovr[k] = lww(a.ovr[k], b.ovr[k])
  for id in keys(a.items) ∪ keys(b.items):
    both    → per-field lww
    only a  → keep iff b.seen[dev(id)] < id     # b never had it
    only b  → keep iff a.seen[dev(id)] < id
lww(x, y) = the one with the larger stamp string
```

- **The one rule that keeps this safe:** a copy may claim `seen[me] = s` only if it holds every item born on this device up to `s`. Across browser tabs, do each local edit as "read the stored copy, merge, edit, write" inside `navigator.locks.request(...)`.
  - The Web Locks API is "Baseline widely available … since March 2022" and needs a secure context (MDN, fetched today).
  - Checkpoint 1 already merged the stored copy before saving (`app.js:117-121`) and on storage events (`app.js:620-628`). Keep that.
- **Treat every input as hostile:** validate types, cap lengths and counts, and drop malformed stamps, as `sanitize()` does (`app.js:34-62`). But **never clamp stamps relative to the receiver's clock** (B4).

### 6.5 Wire format

**Nostr event** (NIP-01/78), one per device slot:

```json
{ "kind": 30078, "pubkey": "<listPubkey>", "created_at": "max(nowSec, lastCreatedAt + 1)",
  "tags": [["d", "<slotTag>"], ["expiration", "<now + 180 days>"]],
  "content": "base64url( iv[12] ‖ AES-GCM(encKey, pad(gzip(JSON(state))), aad = 'll2|' + pubkey + '|' + slotTag) )",
  "id": "sha256(...)", "sig": "BIP-340 signature with the derived key" }
```

- **Compress, then pad** to power-of-two buckets of at least 1 KB, so a relay learns only the size class.
  - `CompressionStream` is "Baseline: Widely available … since May 2023" (MDN, fetched today; the page shows gzip).
  - Measured: a 60-item state is 5,724 bytes of JSON and 825 bytes deflated (`proposed-merge.mjs` output). One record then fits in 1-2 KB, far below every relay's size cap.
- **Expiration:** the NIP-40 `expiration` tag (relays "SHOULD" delete after it) cleans up abandoned lists. Phones republish on open, so live lists never expire.
- **Do not delete other phones' slots with NIP-09.** An `a`-tag deletion removes "all versions … up to the `created_at`" of the deletion (`work/sync/specs/nip09.md:35`), so a slow clock could swallow a later republish. Let expiration do the cleanup.
- **Signatures:** received signatures need not be checked for integrity, because AES-GCM already authenticates the content. Relays check signatures on write.

**MQTT fallback** (same plaintext and ciphertext):
- Topic `<topicRoot>/<slotTag>`, retained, QoS 0; subscribe to `<topicRoot>/+`.
- There is no signature, so anyone can wipe or overwrite a slot. Readers ignore anything that does not decrypt, and each phone repairs its own slot (§6.6).
- A hand-written client is about 80 lines; the subscribe half is in `work/sync/probe-mqtt.mjs`, so mqtt.js (105 KB) is not needed.

### 6.6 Protocol

1. **Open:**
   - Draw the local copy, then focus the input.
   - In the background: derive the keys, lazy-load the vendored, pinned 5 KB signer (self-hosted, never from a CDN, because any third-party script can read `location.hash`; research P5), and open 4-5 relays in parallel.
   - Send `REQ {kinds:[30078], authors:[listPubkey]}`.
2. **Each incoming event:** de-duplicate by id, decrypt (ignore failures), sanitize, merge, save, render (with a highlight). Keep the subscription open for live events.
3. **After each relay's `EOSE` (repair):** if that relay lacks this device's slot, or holds an older `created_at` than the last one published, republish there. Lost or wiped relay copies heal themselves.
4. **Local edit:** stamp, save synchronously, render. Publish after about 150-300 ms (taps grouped together) to every connected relay. An `OK true` marks that relay as up to date.
5. **Absorbing a remote change:** republish this device's slot after about 3 s, only if the content hash changed. This copies the other phone's edits into a second slot for redundancy. The loop stops after one round, because merged copies become equal.
6. **Refresh:** if this device's slot is more than 30 days old, republish on open, which renews the 180-day expiration.
7. **AUTH:** on `["AUTH", challenge]`, or a `CLOSED`/`OK` with `auth-required:`, sign a kind-22242 event with the list key (NIP-42, `work/sync/specs/nip42.md:41-59`) and retry.
8. **Rejections:**
   - `blocked:` or `restricted:` (web-of-trust, paid, kind not allowed): drop that relay for this list.
   - `rate-limited:`: back off.
   - `invalid:` mentioning `created_at`: show "the phone's clock is off". nostr21 (strfry) rejects more than 900 s in the future; nostr.wine more than 300 s.
9. **Wake:** reconnect on `visibilitychange` and `online`, as `app.js:613-618` does.
10. **Relay list:** ship defaults, and also carry a last-writer-wins `relays` register in the list state, so all phones of a list move together when defaults change.
    - Candidate set from today's probes (accepted and read back, long retention seen): relay.primal.net, nostr.oxtr.dev, relay.nostr.net, relay.coinos.io, nostr-pub.wellorder.net.
    - Avoid offchain.pub and bitcoiner.social (web-of-trust after a few writes), nos.lol (read-back failed, stalls) and memlay relays.

### 6.7 What a relay can and cannot learn or do

- **It cannot:** read the title, items or done flags; forge, alter or move records (AES-GCM with bound authenticated data, plus a signature with the derived key); or undo anything by replaying old records (the CRDT absorbs stale copies; prototype check "replay: no effect").
- **It can see:** the list pubkey (a stable pseudonym per list), the number of device slots, edit timing, the padded size class, IP addresses, and the browser `Origin` header (which names the site).
- **It can:** refuse or drop events (availability only). The phones keep the data, and the other relays keep copies.
- **A leaked link** gives anyone full read and write access. Rotation (new secret, new list) remains the remedy, as before.

### 6.8 Limits and risks of this design

- **Relays promise no retention.** A list unopened on every phone for months survives only on the phones; Safari's 7-day storage cap matters here (research lines 149-150), so push the Home Screen install.
- **Policies drift:**
  - 7 of 24 relays I probed were unreachable today.
  - The sibling saw web-of-trust, NIP-05, paid and "kind not allowed" rejections.
  - NIP-78's AUTH rule may spread; this design is compatible if it implements NIP-42.
- **Delete beats a concurrent edit.** Undo must create a new item.
- **The "seen" rule requires disciplined local writes** (Web Locks across tabs). A bug there could silently drop an item. Test it like the merge.
- **Clocks far ahead** (more than 5-15 min) block publishing on relays with a future limit (nostr.wine 300 s, nostr21 900 s) until fixed. A clock far ahead also pushes stamps forward, which is harmless to ordering.
- **The MQTT fallback** violates nobody's code but sits on "testing only" terms, and anyone can wipe it there.

### 6.9 Carry over vs. drop

- **Keep:**
  - The secret in the fragment, HKDF-derived keys, AES-GCM with random IVs and authenticated data, padding, and strict `open()` (`sync.js:30-70`).
  - `sanitize()` on everything from storage or the network (`app.js:34-62`), without the clamp.
  - Merging on storage events (`app.js:620-628`) and on wake (`app.js:613-618`).
  - Migration of old lists from localStorage (`app.js:81-104`).
  - Protected merge tests (`tests/merge.test.js` style), ported to Node.
  - The "one small transport interface" idea (research line 205), reshaped to `publishSlot` / `onRecord`.
  - No third-party scripts.
- **Drop:**
  - `relay/` (Worker, Durable Object, wrangler, write token, compare-and-set protocol) and the `Relay` class.
  - The single shared blob; whole-item last-writer-wins; per-item wall-clock `bump` without a device tie-break; 60-day tombstones; the receiver-relative clamp.
  - mqtt.js; plaintext retained `listolista/v2/<room>/data`; `?room=` links; presence and drafts topics.

## 7. Evidence for the design: prototype test (`node work/sync/proposed-merge.mjs`)

| Check | Result |
|---|---|
| Scenario: tie between two clocks behind, strike vs. delete (old B1) | Both phones converge |
| Scenario: concurrent strike + text edit (old B2) | `pan integral*`: both kept |
| Scenario: stale phone after 200 days (old B3) | Deleted item stays deleted; its offline add survives; converges |
| Scenario: slow clock strikes an item stamped by a clock 1 h ahead (old L2) | The tap wins |
| Scenario: replaying an old copy | No effect |
| Scenario: one shared slot vs. per-device slots, both phones publishing blind | Shared slot shows `pan` (A's `leche` lost); per-device slots show `leche,pan` |
| Random: 3,000 runs. 3 devices with clocks 0, -15 min and +20 min; 60 random steps of add, strike, edit, delete, rename, publish, partial read, relay serving an old copy, relay losing a slot; then everyone syncs | **All converged; no deleted item came back; merge laws (commutative, associative, idempotent) held** |
| Random, tie-heavy: 1,000 runs with equal clocks and 0-1 ms steps | All converged, nothing came back |
| Control: merge that unions items instead of using `seen` | Caught: deleted items came back in **409/500** runs |
| Control: tie-break that ignores the device id (tie-heavy) | Caught: **43/500** runs diverged |

Output line: `10 checks passed; 3000 random runs (3 devices, skewed clocks, lossy relay, replays) converged with no resurrection; merge laws held`.
